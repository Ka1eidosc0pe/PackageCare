# Hackathon submission preparation

This is a checklist and draft narrative. It is not a submission or claim of eligibility/readiness.

## Positioning

PackageCare helps recipients review how a delivery was handled, inspect the exact supporting footage, add what they observed about damage, and prepare a report they control.

The differentiator is the complete handling-to-evidence-to-reviewed-report workflow. Keep claims proportional to measured results. Automated carrier/Amazon escalation is a clearly labeled roadmap concept requiring an authorized integration.

## Before entering

- [ ] Owner confirms eligibility and registers for the hackathon.
- [ ] Real Ring simulator/device interaction and suitable footage verified (Gate A).
- [ ] Real Bedrock handling evaluation, including normal and ambiguous examples, completed (Gate B).
- [ ] Working AWS integration demonstrated and documented for AWS Builder.
- [ ] Production build and meaningful tests pass; full user journeys checked.
- [ ] GitHub repository contains source, assets/generation instructions, and setup/run guidance.
- [ ] Private-repository access granted to the currently required Amazon/Devpost reviewers by the owner; invitations accepted or refreshed as needed.
- [ ] All demo media is owned/authorized and English-language material is ready.
- [ ] Public YouTube/Vimeo demo under three minutes recorded and uploaded by the owner.
- [ ] Per-tool product feedback and actionable friction log prepared from real observations.
- [ ] Reproducible testing/access plan through judging is documented.

## Demo sequence

Lead with the customer's real workflow: Ring delivery → visible handling moment → source evidence → recipient statement → reviewed report. Briefly show ordinary and unclear cases. Show the actual AWS execution and measured results. Finish with the clearly labeled future escalation concept.

Do not portray synthetic fixture analysis as live AI, present a generic upload as Ring simulator integration, claim identity/intent/damage from appearance, invent model accuracy, or show fake carrier submission success.

## Feedback to collect

For every SDK/service used: purpose, onboarding steps, what worked, problems, workaround, performance/reliability observations, and whether we would use it again. Record AWS services explicitly. Use `friction-log.md` and filter out our own implementation errors when describing provider friction.
